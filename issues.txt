Great question. Let me break down the sync mechanism first, then explain the overhead.

  How syncMaxProfit works

  static void syncMaxProfit(MPI_Win win){
      int globalVal;
      MPI_Fetch_and_op(&maxProfit, &globalVal, MPI_INT, 0, 0, MPI_MAX, win);                    
      MPI_Win_flush(0, win);
      if(globalVal > maxProfit) maxProfit = globalVal;                                          
  }                                                                                             
  
  The window setup                                                                              
                                                            
  MPI_Win_allocate(sizeof(int), ...);   // rank 0 exposes one int to everyone
  *win_buf = 0;                                                                                 
  MPI_Win_lock_all(0, win);             // passive target epoch — open for entire run           
                                                                                                
  MPI_Win_lock_all with flag 0 opens a passive target epoch. This means rank 0's memory is      
  accessible by any rank at any time, without rank 0 doing anything — rank 0 doesn't call any   
  MPI function to "receive" these operations. This is what makes it truly one-sided.            
                                                            
  What MPI_Fetch_and_op does                                                                    
  
  It's a single atomic operation at rank 0's memory. Conceptually:                              
                                                            
  // Happens atomically at rank 0's window:                                                     
  globalVal    = win_buf[0]                  // fetch old value
  win_buf[0]   = max(win_buf[0], maxProfit)  // apply MPI_MAX op                                
  // return globalVal to caller                                                                 
                                                                                                
  "Atomic" means no two ranks can interleave between the fetch and the update. If ranks A and B 
  call simultaneously:                                      
  - One goes first: say A reads 500, writes 600                                                 
  - Then B: reads 600, writes max(600, 550)=600                                                 
  - B sees globalVal=600 > maxProfit_B=550 → B updates its local maxProfit=600
                                                                                                
  No rank ever blocks waiting for another. Everyone fires their operation independently.        
                                                                                                
  What MPI_Win_flush(0, win) does                                                               
                                                                                                
  This is not a barrier. It's a one-sided completion guarantee — it says "ensure MY operation   
  has been delivered to rank 0's memory before I proceed." Rank 0 does nothing. It's purely
  local completion, like a memory fence.                                                        
                                                            
  Why it's non-blocking

  Traditional MPI_Allreduce: all ranks must arrive at the same call simultaneously. Rank 7      
  finishes early? It sits and waits for rank 0 to arrive.
                                                                                                
  MPI_Fetch_and_op: rank just fires off an atomic write to rank 0's memory and continues        
  immediately. No rendezvous. No waiting. Each rank runs at its own pace.
                                                                                                
  ---                                                       
  Why you can't sync after every findClique call
                                                
  From the run.log: rank 7 makes 7.2 million findClique calls. Let's cost it out:
                                                                                                
  ┌──────────────────────────────────┬───────────────────────────────┬──────────────────────┐   
  │                                  │    Current (per top-level     │  Every findClique    │   
  │                                  │            vertex)            │         call         │   
  ├──────────────────────────────────┼───────────────────────────────┼──────────────────────┤
  │ Syncs per rank                   │ ~31                           │ ~7,200,000           │
  ├──────────────────────────────────┼───────────────────────────────┼──────────────────────┤   
  │ Time per sync (typical           │ ~2–5 μs                       │ ~2–5 μs              │   
  │ RMA+flush)                       │                               │                      │   
  ├──────────────────────────────────┼───────────────────────────────┼──────────────────────┤   
  │ Total sync overhead              │ ~0.15 ms                      │ 14–36 seconds        │
  └──────────────────────────────────┴───────────────────────────────┴──────────────────────┘   
  
  Even though each individual call is non-blocking and cheap, at 7 million calls the cumulative 
  overhead exceeds the entire compute time. Additionally:   
                                                                                                
  1. Hot-spot contention: all 8+ ranks firing atomic ops at the same memory location — these get
   serialized at rank 0's memory controller. At high frequency this creates queuing delays.
  2. MPI_Win_flush latency: even locally, flushing 7M times means 7M round-trip acknowledgments 
  from rank 0. On an HPC network this is significant.                                           
  
  ---                                                                                           
  The right answer: periodic sync every K calls             
                                                                                                
  void findClique(vector<int>candidates, int currProfit, int currWeight){
      findCliqueCallCount++;                                                                    
      if((findCliqueCallCount & 0xFFFF) == 0)  // every 65536 calls
          syncMaxProfit(win);                                                                   
      ...                                                   
                                                                                                
  With K=65536: ~110 syncs during rank 7's 7.2M calls. Overhead: ~0.5 ms. But rank 7 would pick 
  up rank 4's profit=650 at the ~2M call mark (~6s into processing v=7), and prune the remaining
   2M calls aggressively. That's potentially 5+ seconds saved.                                  
                                                            
  The win handle would need to be passed into findClique or made global (since it's used in     
  syncMaxProfit).
